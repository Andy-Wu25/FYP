## Suggested Section Structure

### 4.X.1 — Vector Database Selection and Architecture

**Key points to cover:**
- ChromaDB was selected as the vector database — an open-source, lightweight embedding store with built-in HNSW (Hierarchical Navigable Small World) indexing.
- Uses `chromadb.PersistentClient` for durable on-disk storage (SQLite-backed with HNSW binary indices).
- Telemetry disabled: `Settings(anonymized_telemetry=False)`.
- Default persistence path: `~/.code-sim/chroma/`.

**Dual-collection design:**
The system maintains two logically separated collections within a single ChromaDB instance:

| Aspect | Private Collection | Public Collection |
|--------|-------------------|-------------------|
| **Name** | `{base}_private` (default: `project_code_private`) | `{base}_public` (default: `project_code_public`) |
| **Scope** | Organisation-scoped; filtered by `org_id` | Global; shared across all users |
| **Source** | Any git repository (local or remote) | Public GitHub repositories only |
| **Query filter** | `WHERE org_id = ?` | Optional `WHERE license IN (?)` |
| **Additional metadata** | `org_id`, `repo_id` | `public_source_id`, `source_url`, `license`, `source_commit`, permalink fields |

Both collections use the same distance metric (configurable, default `cosine`) and HNSW space configuration via `{"hnsw:space": metric}`.

### 4.X.2 — Collection Schema and Data Model

Each record stored in a ChromaDB collection consists of four components:

**1. ID (unique identifier)**
- Private: `SHA-256(org_id : repo_id : file_path : content_hash)` — generated by `make_element_id()` in `core/code_parser.py`
- Public: `SHA-256(public_source_id : file_path : content_hash)` — generated by `_public_element_id()` in `indexing/public_index.py`
- Content-addressable: the same code element always produces the same ID, enabling idempotent upserts.

**2. Embedding (float vector)**
- Generated by the vLLM embedding server (model-dependent dimensionality).
- Represents the semantic meaning of the code element.

**3. Document (source text)**
- The raw source code text of the function/method/class.
- Stored for retrieval and display in results — ChromaDB stores it alongside the vector.

**4. Metadata (structured key-value pairs)**

Private collection metadata:
```
org_id, repo_id, repo_name, file_path,
function_name, kind, start_line, end_line, content_hash
```

Public collection additional metadata:
```
public_source_id, source_url, source_owner, source_repo,
source_commit, source_commit_url, source_file_url,
source_file_commit, license, license_spdx
```

### 4.X.3 — Embedding Pipeline

**Key points to cover:**

**vLLM Integration:**
- The system uses a self-hosted vLLM server exposing an OpenAI-compatible `/v1/embeddings` endpoint.
- Default model: `Octen/Octen-Embedding-8B`.
- Communication via HTTP POST with JSON payload `{"model": "...", "input": [...]}`.
- Configurable via environment variables: `VLLM_BASE_URL`, `VLLM_MODEL`, `VLLM_API_KEY`, `VLLM_BATCH_SIZE`, etc.

**Batch processing:**
- Texts are embedded in batches of configurable size (default 64) to balance throughput and memory.
- Each batch is a single HTTP request to the vLLM server.

**Long text handling (important for paper):**
When `max_chars > 0`, texts exceeding the limit are handled by one of two strategies:

1. **Chunking mode** (`long_text_mode = "chunk"`):
   - Text is split into overlapping windows of `max_chars` characters.
   - Overlap size: `chunk_overlap` (default 512, capped at `max_chars // 8`).
   - Step size: `max_chars - chunk_overlap`.
   - Each chunk is embedded independently.
   - Final vector = component-wise average of all chunk vectors: `v = (1/N) Σ vᵢ`.

2. **Truncation mode** (`long_text_mode = "truncate"`):
   - Text is cut to exactly `max_chars` characters.
   - Single embedding produced.

3. **Unlimited mode** (`max_chars = 0`):
   - Full text passed to the model with no splitting.
   - Relies on the model's native context window.

**Optional input prefix:**
- `VLLM_INPUT_PREFIX` can be set to prepend a task instruction (e.g., `"Represent the following code: "`).
- Applied after chunking, before embedding.

**Embedding config consistency:**
- At index time, the embedding configuration (`max_chars`, `long_text_mode`, `chunk_overlap`, `model`) is saved to `_embedding_config_{type}.json` alongside the database.
- At query time, this config is loaded and used to create the `EmbeddingClient`, ensuring query vectors are generated with identical settings to index vectors.
- First save is canonical; subsequent saves with different config emit a warning but do not overwrite. This prevents accidental vector space misalignment.

### 4.X.4 — Indexing Pipeline (Write Path)

The indexing pipeline transforms source code into searchable vector entries. The complete flow:

**Step 1 — Source file discovery and filtering:**
- Scans repository files (git-tracked or explicit paths).
- Filters out noise: excluded directories (`node_modules`, `.git`, `vendor`, etc.), excluded extensions (`.min.js`, `.lock`, etc.), excluded filenames (`package-lock.json`, etc.).
- Language detection via `identify` library + suffix/hint maps to Tree-sitter grammars.
- Binary file detection and size guard (250 KB cap).

**Step 2 — Code element extraction:**
- Tree-sitter parses each file into an AST.
- Extracts declaration-like nodes: functions, methods, constructors, classes.
- Each element becomes a `CodeElement`: `{id, name, kind, text, start_line, end_line, hash}`.
- Fallback: if no declarations are found (or parse fails), the entire file is treated as a single element.

**Step 3 — ID generation:**
- `make_element_id()` produces a deterministic SHA-256 hash from `(org_id, repo_id, file_path, content_hash)`.
- Content-addressable: unchanged code produces the same ID, so `upsert` is a no-op for unchanged elements.

**Step 4 — Embedding generation:**
- All element texts are collected and passed to `EmbeddingClient.embed_documents()`.
- Batched HTTP calls to vLLM server.
- Long texts chunked and averaged as described above.

**Step 5 — Vector store upsert:**
- Elements grouped by file path.
- For each file, `collection.upsert(ids, embeddings, documents, metadatas)` is called.
- ChromaDB's upsert is idempotent: existing entries with matching IDs are updated, new entries are inserted.

**Step 6 — Stale entry cleanup:**
- After indexing, the set of current IDs is compared against all existing IDs for the repository.
- Stale IDs (elements that were deleted or renamed) are removed in batches of 500.
- This keeps the index synchronised with the current state of the codebase.

### 4.X.5 — Query Pipeline (Read Path)

The query pipeline transforms a code element into a similarity search and returns ranked matches:

**Step 1 — Embedding config resolution:**
- Loads `_embedding_config_{type}.json` from the database directory.
- Creates `EmbeddingClient` with the saved settings to ensure vector space consistency.
- If configs for private and public differ, a warning is logged and environment defaults are used.

**Step 2 — Query embedding:**
- The query code element's text is embedded using the same `embed_documents()` pipeline as indexing.
- Produces a single float vector matching the dimensionality of the indexed vectors.

**Step 3 — Over-fetch from ChromaDB:**
- The system uses an **over-fetching strategy**: requests `pool_size = max(top_k × 4, 20)` results from ChromaDB.
- This provides a larger candidate pool for post-hoc filtering.
- ChromaDB performs HNSW approximate nearest-neighbour search with cosine distance.

**Step 4 — Metadata filtering via `WHERE` clauses:**
- Private queries: `WHERE org_id = ?` (scoped to the organisation).
- Private self-queries: `WHERE org_id = ? AND repo_id = ?` (scoped to a single repo).
- Public queries: optional `WHERE license IN (?)` for license filtering.

**Step 5 — Post-retrieval filtering (`extract_hits()`):**
Three-stage filter applied to the over-fetched pool:
1. **Custom filter** (`include_hit` callback): excludes exact self-matches by checking `(org_id, repo_id, file_path, content_hash)` equality.
2. **Distance threshold**: drops any result where `distance > max_distance` (default 0.15).
3. **Top-K selection**: returns the first K results that pass both filters. Results arrive pre-sorted by distance from ChromaDB.

### 4.X.6 — Operational Concerns

**Snapshot and restore:**
- The `tools/snapshot.py` module provides named snapshot management.
- `cmd_save()`: copies the entire ChromaDB directory (SQLite + HNSW binaries) to a named snapshot directory with `_snapshot_meta.json`.
- `cmd_load()`: restores a snapshot by overwriting the active database directory.
- Enables reproducible experiments and safe rollback.

**Pagination and deletion:**
- Large collections are handled with paginated ID retrieval (`_get_all_ids()` in batches of 5,000).
- Bulk deletions are chunked into batches of 500 to avoid overwhelming ChromaDB.

**Configuration hierarchy:**
```
CLI flags → Environment variables → Saved embedding config → Hardcoded defaults
```

## Key Design Decisions to Highlight in Paper

1. **Dual-collection separation** — Private and public indices are logically isolated but share the same ChromaDB instance and distance metric, simplifying deployment while maintaining access control.

2. **Content-addressable IDs** — SHA-256 hashing of `(org, repo, path, content_hash)` ensures idempotent upserts. Unchanged code is never re-indexed.

3. **Over-fetching with post-hoc filtering** — Requesting 4× the desired results compensates for self-match exclusion and distance thresholds without requiring complex ChromaDB query logic.

4. **Embedding config canonicalisation** — First-write-wins strategy prevents vector space drift when multiple indexing runs use different settings.

5. **Cosine distance metric** — Selected for HNSW because code embeddings benefit from direction-based similarity rather than magnitude-based (Euclidean). Cosine distance is normalisation-invariant, making it robust to varying code element lengths.

6. **Chunked averaging for long functions** — Overlapping chunks with component-wise vector averaging preserves both local and global semantic information from long code elements that exceed the model's effective context.
